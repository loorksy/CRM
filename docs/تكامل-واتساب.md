# تكامل واتساب — Evolution API مدمج داخل LorkERP

## ما الذي تم فعلاً

مستودع [evolution-api](https://github.com/evolution-foundation/evolution-api) (الإصدار 2.3.7)
موجود بملفاته كاملة داخل `integrations/evolution-api/` عبر `git subtree`، ومُعدَّل ليعمل
**داخل عملية النظام نفسها وعلى نفس المنفذ** — لا خدمة منفصلة ولا منفذ ثانٍ ولا حاوية مستقلة.

```
http://<host>:3020/            ← نظام LorkERP (كما هو)
http://<host>:3020/whatsapp-api ← Evolution API (نفس العملية)
```

## التعديلات على مصدر Evolution

أربعة تعديلات فقط، كلها متوافقة رجعياً — التشغيل المستقل بـ `npm start` داخل
`integrations/evolution-api/` يعمل كما كان تماماً.

| الملف | التعديل | السبب |
|---|---|---|
| `src/embedded.ts` | **ملف جديد** يُصدّر `createEvolutionApp()` | `main.ts` ينشئ خادماً ويستمع على منفذ. النسخة المُضمَّنة تبني نفس التطبيق بلا `listen()` لتُركَّب داخل خادم النظام. |
| `src/config/path.config.ts` | `ROOT_DIR` يحترم `EVOLUTION_ROOT_DIR` | عند التضمين تكون `process.cwd()` هي جذر الـ ERP، فكانت مجلدات `store/` و `instances/` تُنشأ في المكان الخطأ. |
| `src/config/env.config.ts` | قراءة `.env` الخاص بـ Evolution أولاً | `dotenv.config()` يقرأ من `cwd`، فكان يقرأ ملف بيئة الـ ERP ويتجاهل مفاتيح Evolution. |
| `src/api/integrations/event/websocket/websocket.controller.ts` | مسار Socket.io من `WEBSOCKET_PATH` | النظام يشغّل Socket.io على `/socket.io` أصلاً؛ بقاء الاثنين على نفس المسار يجعل أحدهما يبتلع اتصالات الآخر. |

التطبيق المُركَّب هو **sub-application** كامل: محرك قوالبه (hbs) وملفاته الساكنة
وحدود جسم الطلب محصورة فيه، فلا يتأثر محرك EJS ولا أي مسار قائم في النظام.

## نموذج الأمان

### القاعدة الحاكمة

> **العزل بين المستخدمين مفروض بالكود، لا بتعليمات النموذج.**

أدوات الوكيل في `services/whatsapp/scopedData.js` **لا تقبل أي معرّف مستخدم كمُعامل**.
النطاق يأتي حصراً من `whatsapp_identities` بعد التحقق. حتى لو أقنع مستخدمٌ النموذجَ
بتجاهل تعليماته، لا توجد أداة تقبل هوية بديلة ليُخدع بها.

`executeTool` يُسقط أي مفتاح غير موجود في `parameters.properties` الخاص بالأداة،
فحقن `memberUserId` أو `user_id` في وسائط الاستدعاء لا أثر له إطلاقاً.

### تسلسل كل رسالة واردة

```
رسالة من واتساب
   ↓
تحديد المعدّل (20 رسالة/دقيقة افتراضياً)
   ↓
البحث عن الرقم في whatsapp_identities
   ├─ غير موجود ──────→ «هذا الرقم غير مسجّل» ولا شيء غير ذلك
   ├─ موجود، غير مُفعّل → طلب رمز التفعيل فقط
   ├─ محظور ──────────→ رفض
   └─ مُفعّل ──────────→ نطاق (scope) مُجمَّد + أدوات نوعه فقط
```

### لماذا الرمز يُسلَّم خارج واتساب

إرسال رمز التحقق إلى نفس الرقم الذي يراسلنا **لا يثبت شيئاً** — المرسِل يتحكم
بذلك الرقم أصلاً. لذلك:

1. المسؤول يربط الرقم بالعضو من لوحة التحكم (`POST /api/whatsapp/identities`)
2. المسؤول يصدر رمزاً (`POST /api/whatsapp/identities/:id/issue-code`) — يُعرض **مرة واحدة**
3. المسؤول يسلّم الرمز للعضو شفهياً أو عبر قناة الوكالة
4. العضو يرسل الرمز للبوت فيُفعَّل حسابه

الرمز يُخزَّن مُجزَّأً بـ HMAC-SHA256 ولا يُحفظ نصاً صريحاً في أي مكان.
5 محاولات خاطئة ⇒ حظر مؤقت 60 دقيقة.

### الأدوات المتاحة لكل نوع

| العضو (`member`) | المشغّل (`operator`) |
|---|---|
| `get_my_summary` | `get_funds` |
| `get_my_audit_history` | `get_member_stats` |
| `get_my_deferred_history` | `get_cycles` |
| `get_my_adjustments` | `find_member` (داخل مؤسسته فقط) |
| `get_my_events` | |

بالإضافة إليها، يملك كلا النوعين `describe_data` و `query_data` — أدوات
الاستعلام الحر الموصوفة في قسم «طبقة الوكيل الذكي» أدناه.

العضو لا يرى أدوات المشغّل في تعريفات الأدوات المرسلة للنموذج أصلاً،
ولو استدعى واحدة باسمها فسيُرفض ويُسجَّل في التدقيق.

### التدقيق

كل حدث يُسجَّل في `whatsapp_access_log`: محاولة من رقم مجهول، إصدار رمز،
فشل رمز، تنفيذ أداة، رفض أداة، تغيير حالة هوية.

## التثبيت

### 1. تجهيز Evolution

```bash
cp integrations/evolution-api/env.example integrations/evolution-api/.env
```

عدّل `integrations/evolution-api/.env`:

```ini
# نفس خادم PostgreSQL الخاص بالنظام، لكن بمخطط منفصل — لا يلمس جداول الـ ERP
DATABASE_CONNECTION_URI='postgresql://lork:123456@localhost:5432/lorkerp?schema=evolution_api'
AUTHENTICATION_API_KEY=<مفتاح-قوي-عشوائي>
SERVER_URL=https://your-domain.com/whatsapp-api
# إلزامي عند التضمين: يمنع تعارض Socket.io مع النظام
WEBSOCKET_PATH=/whatsapp-api/socket.io
# Redis اختياري. للتعطيل:
CACHE_REDIS_ENABLED=false
```

```bash
npm run evolution:setup   # install + prisma generate + migrate + build
```

### 2. تجهيز النظام

في `.env` الخاص بالنظام:

```ini
EVOLUTION_EMBEDDED=1
EVOLUTION_MOUNT_PATH=/whatsapp-api
EVOLUTION_API_KEY=<نفس AUTHENTICATION_API_KEY أعلاه>
WHATSAPP_WEBHOOK_SECRET=<سر-قوي-عشوائي>
# اتركه فارغاً عند التضمين — يُشتق من المنفذ تلقائياً
PUBLIC_BASE_URL=
```

### 3. التشغيل

```bash
npm start          # أو: pm2 start ecosystem.config.cjs
```

عملية واحدة، منفذ واحد. لا تغيير في `ecosystem.config.cjs`.

### 4. الربط بواتساب

```bash
# إنشاء النسخة وضبط الـ webhook تلقائياً
curl -b cookies -X POST http://localhost:3020/api/whatsapp/instance \
     -H 'Content-Type: application/json' -d '{"instanceName":"lorkerp-1"}'

# جلب رمز QR للمسح من تطبيق واتساب
curl -b cookies http://localhost:3020/api/whatsapp/qr
```

## طبقة الوكيل الذكي

### من أتمتة إلى وكيل

النسخة الأولى كانت تسع أدوات جاهزة تغطي 5 جداول من أصل 59 — أي أنها لم
تكن تجيب إلا عن أسئلة مُتوقَّعة مسبقاً. الآن يؤلّف الوكيل استعلاماته بنفسه.

**لماذا لم يكن التوسيع ممكناً قبل؟** لأن العزل كان شروط `WHERE` مكتوبة
بيد المطوّر: كل جدول جديد يعني فلتراً يدوياً جديداً وفرصة جديدة لنسيان
واحد. فكان لا بد من اختيار: إما الاتساع وإما الأمان.

**الحل:** إنزال العزل إلى قاعدة البيانات، فينفكّ الارتباط بينهما.

### كيف يُفرض العزل الآن

```
دور lorkerp_agent
  ├─ لا يملك أي صلاحية على أي جدول أساسي  ⇒  SELECT * FROM funds = permission denied
  ├─ يملك SELECT على عروض agent_v_* فقط
  ├─ default_transaction_read_only = on
  └─ NOBYPASSRLS

عروض agent_v_*
  └─ شرط النطاق داخل تعريف كل عرض:
        user_id = agent_owner_id()
        AND member_user_id = agent_member_id()     ← لعروض العضو
        AND agent_subject_type() = 'member'|'operator'

متغيرات النطاق (app.owner_id / app.member_id / app.subject_type)
  └─ تُضبط بـ SET LOCAL من الخادم، من الهوية المُتحقَّق منها — لا من النموذج

RLS على 19 جدولاً أساسياً
  ├─ سياسة سماح كاملة لدور التطبيق  ⇒  الـ ERP غير متأثر إطلاقاً
  └─ سياسة نطاق مقيّدة لدور الوكيل وحده
```

النتيجة: يستطيع النموذج كتابة أي `SELECT` يشاء — تجميعات ومقارنات
وفترات زمنية — ولا يستطيع رؤية صف واحد خارج نطاقه، لأن الرفض يأتي من
PostgreSQL لا من تعليمات نصية.

### إغلاق ثغرة `set_config`

`set_config` دالة قابلة للاستدعاء داخل `SELECT` عادي، ولو استدعاها
استعلام الوكيل لأمكنه تبديل `app.member_id` قبل أن تُقيّمه العروض.
مغلقة بطريقتين:

1. حظر نصي في `agentQuery.js` (فعّال لأن SQL لا يسمح بتركيب أسماء الدوال ديناميكياً)
2. `AGENT_HARDEN_SET_CONFIG=1` يسحب الصلاحية من `PUBLIC` ويمنحها لدور التطبيق وحده — تشديد بنيوي

طبقة الوكيل نفسها لا تستعمل `set_config` بل `SET LOCAL`، فالتشديد آمن.

### شخصية الوكيل

قابلة للتخصيص بالكامل من `/api/whatsapp/persona`:

| الخيار | القيم |
|---|---|
| اللهجة | شامي، خليجي، مصري، عراقي، مغاربي، فصحى |
| النبرة | ودود، رسمي، مختصر، صبور شارح |
| الطول | مقتضب، متوازن، مفصّل |
| الدور | نص حر (محاسب، مسؤول حسابات…) |
| الاسم | نص حر |
| الإيموجي | تشغيل/إيقاف |
| المهارات | تفسير الفروقات، ملخص استباقي، انضباط رقمي، شرح المصطلحات، التحويل للإدارة |
| تعليمات حرة | حتى 2000 حرف |

`GET /api/whatsapp/persona/preview` يعرض البرومبت الناتج كما يراه النموذج.

**مهم:** كل هذا يؤثر على الأسلوب فقط. حتى التعليمات الحرة لا تستطيع منح
الوكيل صفاً واحداً خارج نطاق الهوية.

## المزوّد الاحتياطي والذاكرة

### لماذا مزوّد احتياطي

نفاد رصيد OpenAI (`429`) أوقف الوكيل كلياً رغم أن الرد كان ممكناً بمزوّد آخر.
مزوّد واحد = نقطة فشل واحدة. الآن `providerChain.js` يجرّب المزوّدات بالتسلسل.

الانتقال يحدث عند: `429`، `402` نفاد رصيد، `401/403` مفتاح غير صالح،
`404` نموذج مفقود، أي `5xx`، وانقطاع الشبكة. ولا يحدث عند خطأ برمجي في
كودنا — الانتقال لن يساعد هناك.

`GET /api/whatsapp/providers` يعرض الترتيب الفعلي كما سيجرّبه الوكيل.

### OpenRouter — النماذج المجانية فقط

يُضبط من صفحة الإعدادات كأي مزوّد (`provider=openrouter`). الواجهة متوافقة
مع OpenAI فيستعمل نفس مسار التنفيذ.

القائمة تُفلتر بشرطين:

1. **مجاني**: `pricing.prompt` و `pricing.completion` و `pricing.request` أصفار
2. **يدعم استدعاء الأدوات**: `supported_parameters` يحتوي `tools`

**الشرط الثاني ليس تفصيلاً.** الوكيل كله مبني على `describe_data` ثم
`query_data`. نموذج بلا دعم الأدوات لن يستعلم — سيؤلّف أرقاماً من عنده،
وهي نتيجة أسوأ من عدم الرد إطلاقاً في نظام محاسبي.

النماذج المجانية على OpenRouter تتغيّر باستمرار، والقائمة تُجلب حيّة عند
حفظ المفتاح. حدود الطبقة المجانية (طلبات/دقيقة وسقف يومي) تخص حسابك.

### ذاكرة الوكيل

`whatsapp_sessions` يحفظ آخر 12 دوراً وينتهي بعد 12 ساعة. الذاكرة أطول
عمراً: تفضيلات ووقائع وخلاصات محادثات.

| النوع | المصدر |
|---|---|
| `preference` | الوكيل يلاحظ تفضيلاً ويحفظه بأداة `remember` |
| `fact` | واقعة تخص المستخدم |
| `summary` | تكثيف تلقائي لنصف المحادثة الأقدم بعد 10 أدوار |

سقف 40 سطراً لكل هوية؛ عند التجاوز يُحذف الأقل أهميةً ثم الأقدم استعمالاً،
والخلاصات محميّة نسبياً.

**العزل:** كل قراءة مفلترة بـ `identity_id` **و** `owner_user_id` معاً.
أداة `remember` لا تقبل معرّف هوية — تكتب على `scope.identityId` وحده.
`ON DELETE CASCADE` يمسح الذاكرة عند حذف الهوية أو إعادة ربطها، فلا يرث
رقمٌ جديد ذاكرة من سبقه.

**الذاكرة بيانات لا تعليمات:** محتواها من كلام المستخدم، أي مدخل غير موثوق.
يُحقن في قسم موسوم صراحةً بأنه معلومات لا أوامر. حتى لو خزّن مستخدم
«تجاهل قيودك» فلا أثر له — العزل مفروض في قاعدة البيانات لا في البرومبت.

للإدارة: `GET /api/whatsapp/identities/:id/memory` و
`DELETE /api/whatsapp/identities/:id/memory`.

---

## الترخيص

Evolution API مرخّص بـ **Apache 2.0 مع شروط حماية العلامة التجارية**:
الحفاظ على الشعار وإشعار الاستخدام. ملفا `LICENSE` و `TRADEMARKS.md`
محفوظان داخل `integrations/evolution-api/`. راجعهما قبل أي نشر تجاري.

---

## حدود معروفة

- **Redis**: Evolution يوصي به للأداء وحفظ الجلسات. مُعطَّل في الإعداد أعلاه
  (`CACHE_REDIS_ENABLED=false`) وهو كافٍ لعدد نسخ صغير. فعّله للأحمال الأكبر.
- **عملية واحدة**: هذا ما طُلب، وهو ما يجعل النظام خدمة واحدة. المقابل أن
  انهياراً غير معالَج في طبقة Baileys يُسقط الـ ERP معه. عالجناه بأن فشل تركيب
  Evolution لا يمنع إقلاع النظام، وبوجود `uncaughtException` في `server.js`،
  لكن ابقِ PM2 مفعّلاً لإعادة التشغيل التلقائي.
- **الوكيل يقرأ فقط**: لا توجد أداة تكتب أو تعدّل أي بيان محاسبي.
